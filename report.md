1. Исследуемая информационная система
Для выполнения лабораторной работы был выбран сервис Wildberries и пользовательский сценарий: поиск товара и просмотр карточки товара (продолжение ЛР №1).

Wildberries — крупнейший российский маркетплейс, позволяющий пользователям искать и покупать товары от множества продавцов. Пользователь работает через веб-интерфейс, который формирует запросы к серверу, а сервер возвращает данные и обновляет состояние страницы.

В ходе исследования были выделены следующие основные компоненты:

браузер пользователя;

интерфейс сайта (frontend);

клиентский JavaScript, управляющий поиском и отображением карточки;

API-сервис, принимающий запросы от клиента (search.wb.ru, card.wb.ru);

backend, реализующий обработку данных;

хранилище данных, в котором сохраняются товары, пользователи, заказы;

внешние сервисы и ресурсы (CDN static.wbstatic.net, basket-XX.wbbasket.ru, аналитика).

Для изучения сетевого взаимодействия использовалась вкладка Network в DevTools. Перед началом сценария список запросов был очищен, после чего были выполнены действия поиска и открытия карточки товара. В результате удалось наблюдать сетевые обращения, обеспечивающие загрузку интерфейса, получение результатов поиска и данных карточки.

2.1. Основные наблюдения
Во время исследования были замечены следующие типы HTTP-запросов:

GET — для загрузки HTML, CSS, JavaScript, изображений и API-запросов поиска/карточки;

POST — для отправки данных корзины, авторизации и аналитики;

OPTIONS — preflight-запросы CORS при кросс-доменных обращениях.

Предположение: запросы обрабатываются API-сервисом, который обращается к поисковому индексу и базе данных товаров, а затем возвращает JSON клиенту.

3. Анализ HTTP-ответов
После выполнения запроса сервер возвращает HTTP-ответ, содержащий статус-код, заголовки и тело ответа. Для анализа были выбраны два запроса: поиск товаров и карточка товара.

3.1. Пример анализа ответа на запрос поиска
Для запроса поиска был получен ответ со статусом 200 OK. Это указывает на успешную обработку запроса.

Основные наблюдаемые заголовки:

Content-Type: application/json — формат данных;

Content-Encoding: gzip — сжатие ответа;

Cache-Control: max-age=... — политика кэширования;

Access-Control-Allow-Origin: * — CORS;

Date — дата и время ответа.

Тело ответа — JSON-объект, содержащий массив data.products со списком товаров. Для каждого товара указаны id, name, brand, salePriceU, rating, feedbacks.

3.3. Наблюдаемые факты и предположения
Наблюдаемый факт: сервер возвращает JSON-ответ после поиска и при открытии карточки товара.

Предположение: backend выполняет поиск по индексу, агрегирует данные о товаре из разных источников и возвращает результат клиенту.

Предположение: часть логики может быть вынесена в отдельные микросервисы, но это нельзя установить напрямую без доступа к серверной реализации.

4. Анализ параметров и передаваемых данных
При выполнении пользовательского сценария браузер передавал серверу информацию, позволяющую понять, какой запрос выполняется и какие данные нужны.

4.1. Параметры запроса
В запросах, связанных с поиском и карточкой, можно выделить следующие типы параметров:

В query string (URL):

query — поисковый запрос;

resultset — тип выдачи (catalog);

sort — сортировка (popular);

dest — регион доставки;

spp — размер скидки;

page — номер страницы;

nm — артикул товара (для карточки).

В заголовках:

User-Agent — браузер и ОС;

Accept — ожидаемый тип ответа (application/json);

Accept-Encoding — поддерживаемые сжатия;

Cookie — идентификатор сессии.

4.2. Где находятся данные
Параметры были расположены следующим образом:

основная часть данных — в query string (URL);

служебные данные — в cookie и заголовках запроса;

тело запроса — отсутствует, так как используется метод GET.

4.3. Какие данные передаются при поиске и просмотре карточки
При поиске товара сервер получает:

какой поисковый запрос ввёл пользователь;

какой регион доставки используется;

какие параметры сортировки и фильтрации применены.

При открытии карточки товара сервер получает:

В ответе сервер возвращает результат операции и данные товара, чтобы пользователь видел актуальную информацию без перезагрузки страницы.

6. Взаимодействие Frontend, API и Backend
Для выбранного пользовательского сценария важно понять цепочку событий от действия пользователя до визуального обновления интерфейса.

6.1. Последовательность событий
Пользователь

Интерфейс (строка поиска)

JavaScript / frontend-логика

HTTP-запрос к API (search.wb.ru)

Backend-сервис

Обработка и поиск данных

HTTP-ответ (JSON)

Обновление интерфейса

Пользователь видит результаты поиска

Клик по товару → HTTP-запрос к card.wb.ru

Backend агрегирует данные о товаре

HTTP-ответ (JSON)

6.2. Конкретное действие
Рассмотрим действие: пользователь вводит поисковый запрос и нажимает Enter.

Пользователь взаимодействует с UI-элементом <input> строки поиска.

Frontend реагирует на событие submit и формирует HTTP-запрос.

Браузер отправляет GET-запрос на search.wb.ru/exactmatch/ru/common/v4/search.

API принимает запрос и передаёт его на backend.

Backend обрабатывает данные: выполняет поиск по индексу, применяет фильтры и сортировку.

Сервер возвращает ответ со статусом 200 OK и JSON со списком товаров.

JavaScript frontend получает ответ и обновляет DOM — отображает список найденных товаров.

Пользователь видит результаты поиска.

Далее при клике на товар:

Frontend формирует GET-запрос к card.wb.ru/cards/v4/detail с артикулом товара.

Backend агрегирует данные из БД, кэша и CDN.

Сервер возвращает JSON с детальной информацией.

Frontend рендерит карточку товара.

Пользователь видит карточку.

6.3. Вывод по архитектуре
В результате исследования было подтверждено, что взаимодействие между клиентом и сервером происходит через HTTP. Браузер не хранит состояние страницы в единственном локальном файле; он получает и отправляет данные через API, что позволяет приложению обновлять интерфейс динамически, без полной перезагрузки страницы.

9. Вывод
В ходе лабораторной работы было проведено исследование HTTP-взаимодействия в веб-приложении Wildberries на выбранном сценарии «поиск товара и просмотр карточки товара». Было установлено, что интерфейс работает через клиентский JavaScript, который отправляет HTTP-запросы к серверу, а сервер отвечает данными и статусами выполнения операции.

Были выявлены следующие важные результаты:

браузер и frontend тесно взаимодействуют для обработки пользовательского действия;

запросы к API выполняются при поиске и при открытии карточки товара;

поиск сопровождается HTTP GET-запросом к search.wb.ru, а карточка — GET-запросом к card.wb.ru;

данные передаются в query string, а также хранятся в cookies;

обратно пользователю приходит JSON, который обновляет интерфейс без полной перезагрузки страницы.

Главный вывод состоит в том, что современное веб-приложение является распределённой системой: пользователь взаимодействует с UI, frontend формирует сеть запросов, API организует обмен данными, а backend обрабатывает их и сохраняет состояние. Важным является также разделение фактов и предположений: факты подтверждены в DevTools, а предположения обозначены как гипотезы, поскольку без доступа к серверной части нельзя установить внутреннюю реализацию с абсолютной уверенностью.
